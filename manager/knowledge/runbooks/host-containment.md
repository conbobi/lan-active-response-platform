## Observed indicators

- Verified process or socket evidence on a Linux endpoint indicating active compromise: an interactive shell holding a network socket, confirmed malicious process tree, or confirmed command-and-control traffic.
- HTTP-only incidents do not qualify: host containment for an HTTP incident is refused and routed to AI Response Assist, because HTTP evidence does not identify a process.

## Required evidence

- Process identity (PID, process start time, executable path) or socket evidence tied to the same Agent.
- Confirmation that the endpoint is the affected asset and not only the observer of traffic.
- Asset role and business impact of losing network connectivity.

## ATT&CK mapping

- Containment is a response, not a technique; map ATT&CK only from the incident evidence that justified it.

## Alternative explanations

- The suspicious socket belongs to an administrator session or a legitimate service.
- The observed traffic was generated by a scanner against the endpoint rather than by the endpoint.

## Investigation steps

- Confirm the Agent is online and authenticated before dispatching; containment is an ACK-confirmed command, not an optimistic state change.
- Check whether legacy containment (/tmp/isolated) is active: in that case scoped isolation refuses and requires local recovery.
- Record a snapshot; the response action service captures one before dispatch.

## Response options

- isolate: the Agent creates the nftables table inet larp_containment with drop policies on input, output and forward at priority -150. It keeps loopback, IPv6 neighbor discovery, DNS (port 53) and the Manager channel: the resolved Manager addresses and the current WebSocket peer on the Manager port remain allowed, so the Agent can still receive commands.
- unisolate: deletes the larp_containment table. Use it after cleanup is verified.
- Isolation is stateful: it has anti-flapping cooldown (default 600 seconds) and an automatic rollback timer (default 300 seconds) unless configured otherwise.

## Execution prerequisites

- Explicit operator confirmation (confirmed=true); system, policy_engine and risk_assessment actors cannot satisfy it.
- An enrolled Agent with nftables; existing UFW and Docker rules are preserved because containment uses its own table.
- No active cooldown for the same action on the Agent.

## Operational risks

- All non-Manager traffic stops, including legitimate service traffic and SSH from administrators.
- If the Manager address changes (DNS) after isolation, the Agent may lose its channel.
- Automatic rollback may re-open the host before cleanup if the timer is left at its default.

## Rollback guidance

- Use unisolate from the Agents page; the action becomes applied only after the Agent ACK.
- Emergency recovery from the out-of-band console when SSH and the Manager channel fail: stop larp-agent.service and larp-firewall-apply.service, start larp-firewall-rollback.service, review journalctl for the apply, rollback and recover units, then check ss -H -ltnpe and ufw status verbose.
- If the state is rollback_failed: keep the Agent stopped, set LARP_UFW_CONTROL=0 in network.env, compare /var/lib/larp-agent/firewall-transaction.json with configuration and journal, restore only verified UFW files or the approved SSH path. Avoid resetting or flushing the whole firewall; keep Docker, containment and manual policies.
